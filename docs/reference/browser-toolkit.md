# Browser toolkit

The public site on GitHub Pages: the notices, the docs, the rules and their evaluation, and tools that run the same analysis as the CLI in the browser, compiled to WASM from [`sc-wasm`](../../crates/sc-wasm/README.md). Nothing a visitor pastes or loads leaves the browser.

## Building and serving

```sh
scripts/ci/build-site.sh                    # WASM modules, then every page, into _site/
scripts/ci/build-site.sh --pages-only       # pages only, reusing the built modules
python -m http.server -d _site 8080         # then open http://localhost:8080
```

`_site/`, `site/pkg/` (the engine, and the tools module in `site/pkg/tools/`) and `site/pkg-rules/` are generated and gitignored. CI builds them at deploy ([runner](runner.md)). Set `SITE_BASE_URL` for the feed and sitemap; it defaults to `http://localhost:8080/`.

## How the site is built

The pages are static HTML generated by the `sc-site` binary in [`sc-publish`](../../crates/sc-publish/README.md). It reads committed inputs only:

- `notices/*.md`, each checked as `notice lint` checks it;
- `docs/**/*.md`, rendered with a table of contents (links to other docs go to their pages, links to other repository files go to GitHub);
- `rules/default.toml`, for the rules explorer;
- `samples/eval/*.ndjson` and `coverage-allow.txt`, for the evaluation summary (also served as `assets/eval-summary.json`), each file's labels marked with its name for the per-file slices;
- `samples/showcase/*.ndjson`, the synthetic records the landing page walks through, the workbench example loads and the showcase bundle is made from ([showcase](../../samples/showcase/README.md)); a record not marked synthetic fails the build;
- `keys/bundle-signing.pub` when git tracks it, the bundle signing keys ([agent-facing files](#agent-facing-files)); a file that does not parse fails the build;
- the static files in [`site/`](../../site/js/site.js): styles, page scripts and the built WASM modules.

It refuses any path under `data/` or `$SWARMCHASE_DATA`, so watch data and case files cannot reach the site. Unreviewed leads never appear on it. The one input that is not committed is optional: a snapshot of the providers' range files and key directories for the identity page, read only as [identity](identity.md#the-snapshot) describes.

## Pages

| Path | What it shows |
|---|---|
| `/` | The mission and the method walked through the synthetic showcase, then the latest notices. |
| `/notices/` | Every notice, filterable by status, provider, sector, affected host, text and update date; one page per notice. |
| `/methodology/`, `/docs/` | The methodology and every other doc. |
| `/docs/manual/` | The Field Manual, with section and glossary links and a pager. |
| `/docs/manual/sections/` | Every Field Manual section by id, with search. |
| `/operators/` | The operators' guide, with a link to the workbench's access-log preset. |
| `/rules/` | One card per rule, filterable by every SC-T tactic, each with a URL tester; an editor and an in-browser evaluation. |
| `/eval/` | The [summary](evaluation.md#summary-json) of the bundled rules on the labelled set, every slice as a forest plot; tiers recomputed in the page for edited rules. |
| `/analyze/` | The workbench. |
| `/unwrap/` | The layers inside one URL, the rules each triggers, and the URL's score and tier. |
| `/identity/` | The agents an operator's log declares, checked against the providers' published ranges and keys ([agent identity](#agent-identity)). |
| `/tools/` | Evidence bundle check, `security.txt` reader, defang. |
| `/llms.txt`, `/llms-full.txt`, `/.well-known/` | Plain files for AI agents and their operators ([agent-facing files](#agent-facing-files)). |
| `/submit/` | Report a swarm: a form that builds an [SC-Submission](../specs/submission-v1.md) document in the page, and how to send it. |

The navigation groups the pages under Learn, Investigate and Reference. Each group is a `<details>` menu, so it works without scripts.

The index is a plain table without scripts; with them, a filter form appears and keeps its state in the URL hash (`#sector=health&from=2026-08-01`), so a filtered view can be linked. On phones each notice is a card and the form starts folded.

Each notice page shows its status and stage (indicators only, or the date of its latest naming update), the rules and toolkit version, the body, then its dated updates as a timeline (corrections and retractions marked, statements quoted verbatim with who they are from). Affected hosts appear only once a naming update names them. `notices/index.json`, `notices/<id>.json` and `notices/feed.xml` are written as `notice build` writes them.

## Report a swarm

`/submit/` is for agents, researchers and operators who saw agent activity. A form builds a valid [SC-Submission v1](../specs/submission-v1.md) document as they fill it in: who is reporting (and whether it is an AI agent), the claim, and evidence items typed by how they can be checked. The page checks each item's identifying fields as the schema does, shows the JSON as inert text, and offers it to copy or download. It sends nothing: the CSP allows no request but the site's own files and `form-action 'none'` blocks submission. It then names the ways to send the file ([transports](inbox.md#transports)) and says what the project does with it. An agent can skip the form and write the document from the spec and the [schema](../../schemas/sc-submission-v1.json).

## The landing page

The landing page walks one synthetic incident through the method: unwrap, match, link, time, grade agent likelihood, assess scope, attribute, report. Every step has prose, a figure drawn by the generator, its table and the Field Manual sections it rests on, so the page reads without scripts. On phones every figure after the first starts folded, so the walk reads as text first.

The match step draws one record's score as its contributions: each independence group once, context hits under their cap, and weight that fired but does not count as dashed outlines. The scope step draws each cluster's four questions and S1 to S7 tests, with payload present and out of scope in different shapes. *Run it live* loads the engine, re-runs the showcase in the page, and adds an unwrap box for any URL, the runs with zoom, the interaction graph, each cluster's agent-likelihood ladder and each cluster's scope tests.

Until there is a real notice, the notices section shows the indicator notice the engine drafts from the showcase, marked as a synthetic example: each affected host appears by class, as stage one publishes it. Plant signals and declared testing never appear on the landing page.

## The workbench

The workbench analyses pasted or loaded records, including an operator's own access log (`/analyze/#preset=access-log`; see [for operators](../guides/for-operators.md#check-your-own-logs)). *Try an example* loads the synthetic showcase.

*Analyze* is offered once there is input. An input from which no record is read shows no dashboard: an alert says nothing was read, quotes the first problem the parser met, and lists the formats the workbench reads. After a run the records box folds to a line with the record count and *Edit*, so the clusters sit under the summary.

On a wide screen it has three panes: the records and clusters, the views, and the context of what is selected. Phones step through them. The views are:

- **Runs**: a lane per cluster and a bar per run, pauses shaded, shared pauses outlined;
- **Runs** zoom: drag across the plot, or focus the chart and use `+`, `-`, the arrow keys and `0`;
- **Fleet**: clusters as nodes and the hints between them (shared pauses, probe chains, payload dialects, soft links, candidate fleets) as edges, one style per soft-link kind in the legend; a kind the page does not know is drawn in the generic style under its own name;
- **Swarm**: runs as nodes on a time axis and the interaction hints between them (S1 to S5) as arcs, styled by kind and weighted by strength;
- **Rules × clusters**: a heatmap whose cells filter the records;
- **Rhythm**: records by weekday and hour, UTC;
- **Endpoints × time** and **Hourly**.

The context panel shows a selected cluster's agent-likelihood ladder (every rung from L0 to L5, the signals on each, counter-signals, and any cap that holds the grade below what its signals reach; the grade is labelled unmeasured on held-out data), its scope assessment, its sources and corroboration, its tactics as a small bar chart, its timing, and the hints the analysis found, among them relay stacks, benchmark targets, stale knowledge and the languages of prose in parameters.

The scope section ([SC-FM 15](../manual/15-misalignment.md)) answers the four questions as separate chips (payload present, agent present, out of scope, coordinated), states the evident task and the target classes reached, and lists the S1 to S7 tests with their outcome, detail and records; selecting a record shows it. Payload present is observed from the tier and drawn plainly; out of scope is an inference from the tests and drawn in the alert colour, so a payload in scope reads differently from scope exceeded. A selected record whose score is less than its rule weights add to says why (groups and the context cap).

*Show attribution layers* lists the developer, host, harness and model-family candidates, gated at the naming level chosen for the report. Plant signals sit in a collapsed *Internal review* section: they concern the visitor's own file and never appear on a generated page. A signal most clusters in the input carry shows its base rate and is marked as context that does not count toward review. Declared testing is left out: the page drops it on receipt, and it reaches only an *Internal case notes* draft, as in the CLI.

The links panel lists shared pauses, dialects, probe chains, common features, escalations, candidate fleets, soft links and interaction hints. Chains and escalations timed by archive captures show no pace.

Every view has a table view. Every mark that selects something is a keyboard button (Enter or Space), focus stays on it after the views redraw, and Escape clears the selection. Edges, shared pauses and rhythms are hints to check, not evidence ([methodology](../methodology.md#descriptive-hints)). The selection is kept in the URL hash as ids only (a cluster key, a record number, a rule id), never hosts or URLs.

The last step drafts a disclosure, loading the tools module on *Draft the report* or when the section scrolls into view. It follows the CLI's naming gate: pick the weakest evidence that may name a developer, and paste claims from case work (the JSON `swarmchase report --claims` reads). Outside case notes, a developer below that level is not named ([attribution](../methodology.md#attribution-levels-and-the-naming-gate)).

## Agent identity

`/identity/` checks the AI agent identities an operator's own log declares, with the tools module's `identity_check` as `swarmchase identity check` runs it ([identity](identity.md)). The log input works as the workbench's: paste or load, a format, a field map naming the host. *Try an example* checks a synthetic log from documentation addresses against synthetic range files, labelled as such.

The result counts every class (signature verified, address verified, in range undeclared, signature unchecked, user agent claim only, signature failed, spoofed, none) and each provider product per class, lists spoofed records first in an alert, then every record with a declared identity: client address, class, provider, product or signer, the file that decided it, and the reason. Records are text; a signer URI and every detail are defanged.

The providers' files table lists each range file and key directory in the catalog with its address as text, which copy is in use (the build's snapshot with its fetch date and age, the operator's own copy, or none) and a picker for a newer copy. *Load files* takes several at once by the names `identity refresh` writes (`<id>.json`) or the last part of a catalog URL; a name two files share, such as `http-message-signatures-directory`, is loaded from its row. The page never fetches a provider's file ([why](identity.md#in-the-browser)); without files, it says every declaration stays a claim.

## Sharing sightings

Under the report, *Share sightings* turns the analysis into an [SC-Sightings v1](../specs/sightings-v1.md) file, so an operator who checked its own log can let the same swarm be matched across operators without sending the log. *Prepare sightings* loads the tools module and shows the whole file, with a list of what it holds and what it never holds; *Download* saves exactly the text shown. Ticking *Include my host names* or editing the optional description redraws the preview first.

The file carries keyed hashes of each flagged cluster's linking features and captured secrets, its scaffold, its hour buckets, client ASNs and its grade; never a URL, path, query value, address, user agent or cookie. The page sends nothing; the operator chooses whether to send the file, and to whom ([for operators](../guides/for-operators.md#share-sightings)).

## The Field Manual

The manual's pages link `FM-n.m` section ids and `SC-Tn` tactic ids in running text to their sections, and the first use on a page of each multi-word glossary term to its definition, with the short definition as a tooltip. Each page ends with previous and next; the hand-written index, previous and next line each chapter opens with, for reading on GitHub, is dropped. The section index lists every section; its search runs in the page over `assets/fm-index.json` (ids, titles, chapters and the start of each section's text), so no module loads.

## Rules explorer

Each rule card links its tactic and its Field Manual section, and names its independence group if it has one. *Test a URL* unwraps a URL with the engine, says whether that rule fires and on which layer, and lists the other rules that fire; the URL is decoded, never opened, and shown defanged. The tactic filter lists SC-T1 to SC-T9; SC-T8 and SC-T9 are cluster- and fleet-level judgments that no rule makes, and the page says so.

## Edited rules

The rules page edits the rules in place. Saved edits are kept in that browser and used by the workbench, the unwrap tool, the bundle check and the evaluation page, which say so. *Test against labelled set* scores the bundled and the edited rules side by side and lists records whose tier changed ([evaluation](evaluation.md)).

The WASM modules read rules as JSON. Edited rules are TOML, as the CLI reads them, and a small second module (`sc-rules-wasm`) converts them; it loads only when there are edited rules. The browser module's regex has no Unicode property classes (`\p{…}`); a rule that needs one works in the CLI only.

## Evidence bundles

The tools page checks an evidence bundle. Pick its files or its folder, or *Load the showcase bundle*, and the page:

1. checks `MANIFEST.sha256.sig` in the tools module against the keys the site publishes (read from `bundle_signing` in its `swarm-report.json`, so a site without a key file is never asked for one), and shows the bundle as signed by its key id, signature invalid (which fails the check), unsigned, or not checked when the site publishes no key ([signed bundles](cases.md#signed-bundles));
1. checks each SHA-256 against the manifest;
2. re-runs the analysis with the bundled rules, or the edited ones;
3. compares every tier and cluster with the stamp, as `case verify` does;
4. shows the stamp with the method and evaluation snapshot it cites, the attribution layers, the runs per cluster, the clusters, any candidate fleets and escalations, and the records, defanged.

The attribution table has a row per layer (developer and operator, hosting and runtime, harness and framework, model family) with each party or candidate, its label (Confirmed, Suspected, Possible, Unattributed) and the strongest likelihood word that label allows, the evidence, and the claim tag. Developers are shown only as a report at the default naming level would name them. Pick the case's `claims.json` (the array `report --claims` reads) with the bundle to merge in claims from case work.

The showcase bundle is made at site build from the showcase records, as `case bundle` makes one, under the bundled rules and with their figures on the labelled set. Its case id is `synthetic-showcase`, and the page labels it synthetic when it shows it. It lets a visitor see the check work without a real bundle. It is never signed: a signature would vouch for records nobody collected.

## Loading and size

The browser runs three modules, each built with its own size budget:

| Module | Loads |
|---|---|
| Engine (`sc-wasm`) | On arrival on the workbench and unwrap pages; on the landing, rules and tools pages when asked. |
| Tools (`sc-wasm --features tools`) | For report drafts, attribution layers, the bundle check, the `security.txt` reader, the identity check and the labelled eval. |
| Rules converter (`sc-rules-wasm`) | Only when there are edited rules. |

The tools module carries a copy of the analysis: a report draft re-runs the analysis there on the same input, which is deterministic, so cluster ids and keys match the engine's. Keeping drafts, bundle checks and evaluation out of the engine keeps the module every analysis page downloads small. Other pages load no WASM.

The tools page preloads nothing. The bundle check and the `security.txt` reader load the tools module on first use, and defang loads the engine. Each card has its own status line, so a module that fails to load leaves the other cards working, and the next use retries it. A loading message gives the module's download size, gzip-compressed as the host serves it; the build measures it. The only render-blocking script is the few lines of `theme.js`, which apply a stored theme before the first paint.

Scripts, the stylesheet and the WASM modules are published under content-hashed names (`js/site.<hash>.js`): GitHub Pages sets its own cache headers, so a changed file gets a new name and a cached one is never stale. The generator rewrites the references in pages and between modules, and `check-site.py` fails a page that loads an unhashed asset. Until a module is ready the page says so and its controls stay disabled. The release build fails when any module is over its budget (the engine's is 1.5 MiB) and prints each module's size and headroom.

## Agent-facing files

The build writes four files that tell an AI agent, or the person who runs it, what the project is and how to report to it. Code: [`agents.rs`](../../crates/sc-publish/src/agents.rs).

| Path | Format |
|---|---|
| `llms.txt` | The [llms.txt](https://llmstxt.org/) convention: title, summary, sections of links. |
| `llms-full.txt` | `llms.txt`, then the full text of the policies, the guides for operators and providers, and the submission spec. |
| `.well-known/security.txt` | RFC 9116, for the project itself; `Expires` is 180 days after the build. |
| `.well-known/swarm-report.json` | The same reporting facts as JSON; `descriptor` names its version. |
| `keys/bundle-signing.pub` | The bundle signing keys, only when the repository commits that file. |

They point at the submission page (`submit/`), the submission spec (`docs/specs/submission-v1.md`) and its schema (`schemas/sc-submission-v1.json`), and the private contact. They state that a person reads every submission, that nothing is published unreviewed, and that each claim is checked against independent public records before it reaches a report or notice.

The text is plain statements of fact. It never addresses the reader as a system prompt would, never asks an agent to do anything beyond an optional report, and never asks it to contact anyone else. It names only this site's pages and the repository, never a host from a record.

Both `.well-known` files say whether evidence bundles are signed. `swarm-report.json` carries `bundle_signing`: `{"signed": false}`, or the algorithm, the key file's URL and each key's id and base64 public key. `security.txt` says it in a comment, because RFC 9116 has no field for it: `Encryption` names a key for encrypting reports sent to the project, the opposite direction, and an unregistered field would read to a parser as a contact detail. The providers page carries the key id, or says no key is published yet.

No convention for a "where to report agent activity" descriptor exists. Agent cards and plugin manifests describe an agent or its API, not an intake, so `swarm-report.json` is a plain document under a well-known path (RFC 8615). The site is a GitHub Pages project site (`<owner>.github.io/<repo>/`), so the files sit under the project path, not the host root that RFC 9116 and RFC 8615 name, and a tool that looks only at the root does not find them. Every page therefore links them: a `rel="alternate"` link to `llms.txt` in its head, and links to `llms.txt`, the submission page and `security.txt` in its footer. The Pages upload includes hidden files so `.well-known/` is published.

## Page references

Every page and agent-facing file carries a canary token: a reference distinct per file and per month (`swc-<YYMM>-<12 characters>`). A token found in a public record shows that something read that surface and repeated the token, no earlier than that month. That may be an agent; the token never says who.

The build embeds tokens when `SWARMCHASE_CANARY_SEED` holds the secret seed, and drops the reference line when it is unset, so a fork or a CI run without the secret builds cleanly ([configuration](configuration.md#canary-tokens)). Tokens are inert, the narrow exception in the passivity test ([FM-3.2](../manual/03-sources.md#fm-32-passivity-test)): no instruction, nothing asked of the reader, no third party, and only on hosts the project controls.

A token is an HMAC of the file's path and the month under the seed. The month is in clear, the path is not, and neither the seed nor any other token can be worked out from published ones, so a copy cannot be backdated. Code: [`canary.rs`](../../crates/sc-core/src/canary.rs).

After a build with a seed, `swarmchase canary register _site` checks each token against the seed and records it in `<data>/canary/registry.json`. `canary scan <records>` and every watch run look for registered tokens in records ([watch](watch.md#canary-sightings)). A sighting says that a surface was read and the token repeated, never who: anyone can copy a token from the page, so a token never links or merges records ([methodology](../methodology.md#linking-into-clusters)).

## Accessibility

Every page has a banner, navigation, main and footer landmark, one `h1` and headings in order, a skip link and a visible focus ring. Charts are labelled groups with a table view. Status and tier colours reach 4.5:1 against every surface in both themes, and motion stops under `prefers-reduced-motion`.

## Safety

Records, notices, claims and edited rules can carry attack payloads, so the site treats them as inert text.

- Every page carries a strict Content-Security-Policy: only the site's own scripts, styles and WASM modules, no inline script or style, no requests elsewhere.
- Generated pages escape every value; page scripts insert text, never HTML. URLs from records are shown defanged and never as links.

[`check-site.py`](../../scripts/ci/check-site.py) checks the sources in CI and the pre-commit hook, and every generated page and the build's inputs after a build. [`site-xss-check.mjs`](../../scripts/site-xss-check.mjs) builds the site with a hostile notice, loads every page in headless Chrome, drives the workbench with XSS probes, hostile claims and hostile edited rules, picks a hostile evidence bundle in the bundle viewer, checks the notice filters on synthetic notices (`crates/sc-publish/tests/fixtures/notices/`, never published), and fails if any of them runs; CI runs it at deploy.

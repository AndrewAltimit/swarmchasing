# Browser toolkit

The public site on GitHub Pages: the notices, the docs, the rules and their evaluation, and tools that run the same analysis as the CLI in the browser, compiled to WASM from [`sc-wasm`](../../crates/sc-wasm/README.md). Nothing a visitor pastes or loads leaves the browser.

## Building and serving

```sh
scripts/ci/build-site.sh                    # WASM modules, then every page, into _site/
scripts/ci/build-site.sh --pages-only       # pages only, reusing the built modules
python -m http.server -d _site 8080         # then open http://localhost:8080
```

`_site/`, `site/pkg/` (the engine, and the tools module in `site/pkg/tools/`) and `site/pkg-rules/` are generated and gitignored. CI builds them at deploy ([runner](runner.md)). Set `SITE_BASE_URL` for the feed and sitemap; it defaults to `http://localhost:8080/`.

## How the site is built

The pages are static HTML generated by the `sc-site` binary in [`sc-publish`](../../crates/sc-publish/README.md). It reads committed inputs only:

- `notices/*.md`, each checked as `notice lint` checks it;
- `docs/**/*.md`, rendered with a table of contents (links to other docs go to their pages, links to other repository files go to GitHub);
- `rules/default.toml`, for the rules explorer;
- `samples/eval/*.ndjson` and `coverage-allow.txt`, for the evaluation summary (also served as `assets/eval-summary.json`), each file's labels marked with its name for the per-file slices;
- `samples/showcase/*.ndjson`, the synthetic records the landing page walks through and the workbench example loads ([showcase](../../samples/showcase/README.md)); a record not marked synthetic fails the build;
- the static files in [`site/`](../../site/js/site.js): styles, page scripts and the built WASM modules.

It refuses any path under `data/` or `$SWARMCHASE_DATA`, so watch data and case files cannot reach the site. Unreviewed leads never appear on it.

## Pages

| Path | What it shows |
|---|---|
| `/` | The mission and the method walked through the synthetic showcase, then the latest notices. |
| `/notices/` | Every notice, filterable by status, provider, sector, affected host, text and update date; one page per notice. |
| `/methodology/`, `/docs/` | The methodology and every other doc. |
| `/docs/manual/` | The Field Manual, with section and glossary links and a pager. |
| `/docs/manual/sections/` | Every Field Manual section by id, with search. |
| `/operators/` | The operators' guide, with a link to the workbench's access-log preset. |
| `/rules/` | One card per rule, filterable by every SC-T tactic, each with a URL tester; an editor and an in-browser evaluation. |
| `/eval/` | The [summary](evaluation.md#summary-json) of the bundled rules on the labelled set, every slice as a forest plot; tiers recomputed in the page for edited rules. |
| `/analyze/` | The workbench. |
| `/unwrap/` | The layers inside one URL and the rules each triggers. |
| `/tools/` | Evidence bundle check, `security.txt` reader, defang. |

The navigation groups the pages under Learn, Investigate and Reference. Each group is a `<details>` menu, so it works without scripts.

The index is a plain table without scripts; with them, a filter form appears and keeps its state in the URL hash (`#sector=health&from=2026-08-01`), so a filtered view can be linked. On phones each notice is a card.

Each notice page shows its status, its dated updates as a timeline (corrections and retractions marked, statements quoted verbatim with who they are from), the rules and toolkit version, and the body. `notices/index.json`, `notices/<id>.json` and `notices/feed.xml` are written as `notice build` writes them.

## The landing page

The landing page walks one synthetic incident through the method: unwrap, match, link, time, grade agent likelihood, attribute, report. Every step has prose, a figure drawn by the generator, its table and the Field Manual sections it rests on, so the page reads without scripts. *Run it live* loads the engine, re-runs the showcase in the page, and adds an unwrap box for any URL, the runs with zoom, the interaction graph, and each cluster's agent-likelihood ladder.

Until there is a real notice, the notices section shows the public notice the engine drafts from the showcase, marked as a synthetic example. Plant signals and declared testing never appear on the landing page.

## The workbench

The workbench analyses pasted or loaded records, including an operator's own access log (`/analyze/#preset=access-log`; see [for operators](../guides/for-operators.md#check-your-own-logs)). *Try an example* loads the synthetic showcase.

On a wide screen it has three panes: the records and clusters, the views, and the context of what is selected. Phones step through them. The views are:

- **Runs**: a lane per cluster and a bar per run, pauses shaded, shared pauses outlined;
- **Runs** zoom: drag across the plot, or focus the chart and use `+`, `-`, the arrow keys and `0`;
- **Fleet**: clusters as nodes and the hints between them (shared pauses, probe chains, payload dialects, soft links, candidate fleets) as edges, one style per soft-link kind in the legend; a kind the page does not know is drawn in the generic style under its own name;
- **Swarm**: runs as nodes on a time axis and the interaction hints between them (S1 to S5) as arcs, styled by kind and weighted by strength;
- **Rules × clusters**: a heatmap whose cells filter the records;
- **Rhythm**: records by weekday and hour, UTC;
- **Endpoints × time** and **Hourly**.

The context panel shows a selected cluster's agent-likelihood ladder (every rung from L0 to L5, the signals on each, counter-signals, and any cap that holds the grade below what its signals reach; the grade is labelled unmeasured on held-out data), its sources and corroboration, its tactics as a small bar chart, its timing, and the hints the analysis found, among them relay stacks, benchmark targets, stale knowledge and the languages of prose in parameters.

*Show attribution layers* lists the developer, host, harness and model-family candidates, gated at the naming level chosen for the report. Plant signals sit in a collapsed *Internal review* section: they concern the visitor's own file and never appear on a generated page. Declared testing is left out: the page drops it on receipt, and it reaches only an *Internal case notes* draft, as in the CLI.

The links panel lists shared pauses, dialects, probe chains, common features, escalations, candidate fleets, soft links and interaction hints. Chains and escalations timed by archive captures show no pace.

Every view has a table view. Every mark that selects something is a keyboard button (Enter or Space), focus stays on it after the views redraw, and Escape clears the selection. Edges, shared pauses and rhythms are hints to check, not evidence ([methodology](../methodology.md#descriptive-hints)). The selection is kept in the URL hash as ids only (a cluster key, a record number, a rule id), never hosts or URLs.

The last step drafts a disclosure, loading the tools module on *Draft the report* or when the section scrolls into view. It follows the CLI's naming gate: pick the weakest evidence that may name a developer, and paste claims from case work (the JSON `swarmchase report --claims` reads). Outside case notes, a developer below that level is not named ([attribution](../methodology.md#attribution-levels-and-the-naming-gate)).

## The Field Manual

The manual's pages link `FM-n.m` section ids and `SC-Tn` tactic ids in running text to their sections, and the first use on a page of each multi-word glossary term to its definition, with the short definition as a tooltip. Each page ends with previous and next. The section index lists every section; its search runs in the page over `assets/fm-index.json` (ids, titles, chapters and the start of each section's text), so no module loads.

## Rules explorer

Each rule card links its tactic and its Field Manual section. *Test a URL* unwraps a URL with the engine, says whether that rule fires and on which layer, and lists the other rules that fire; the URL is decoded, never opened, and shown defanged. The tactic filter lists SC-T1 to SC-T9; SC-T8 and SC-T9 are cluster- and fleet-level judgments that no rule makes, and the page says so.

## Edited rules

The rules page edits the rules in place. Saved edits are kept in that browser and used by the workbench, the unwrap tool, the bundle check and the evaluation page, which say so. *Test against labelled set* scores the bundled and the edited rules side by side and lists records whose tier changed ([evaluation](evaluation.md)).

The WASM modules read rules as JSON. Edited rules are TOML, as the CLI reads them, and a small second module (`sc-rules-wasm`) converts them; it loads only when there are edited rules. The browser module's regex has no Unicode property classes (`\p{…}`); a rule that needs one works in the CLI only.

## Evidence bundles

The tools page checks an evidence bundle. Pick its four files or its folder, and the page:

1. checks each SHA-256 against the manifest;
2. re-runs the analysis with the bundled rules, or the edited ones;
3. compares every tier and cluster with the stamp, as `case verify` does;
4. shows the stamp with the method and evaluation snapshot it cites, the attribution layers, the runs per cluster, the clusters, any candidate fleets and escalations, and the records, defanged.

The attribution table has a row per layer (developer and operator, hosting and runtime, harness and framework, model family) with each party or candidate, its label (Confirmed, Suspected, Possible, Unattributed) and the strongest likelihood word that label allows, the evidence, and the claim tag. Developers are shown only as a report at the default naming level would name them. Pick the case's `claims.json` (the array `report --claims` reads) with the bundle to merge in claims from case work.

## Loading and size

The browser runs three modules, each built with its own size budget:

| Module | Loads |
|---|---|
| Engine (`sc-wasm`) | On arrival on the workbench and unwrap pages; on the landing page and rules page when asked. |
| Tools (`sc-wasm --features tools`) | For report drafts, attribution layers, the bundle check and the labelled eval. |
| Rules converter (`sc-rules-wasm`) | Only when there are edited rules. |

The tools module carries a copy of the analysis: a report draft re-runs the analysis there on the same input, which is deterministic, so cluster ids and keys match the engine's. Keeping drafts, bundle checks and evaluation out of the engine keeps the module every analysis page downloads small. Other pages load no WASM. The only render-blocking script is the few lines of `theme.js`, which apply a stored theme before the first paint.

Scripts, the stylesheet and the WASM modules are published under content-hashed names (`js/site.<hash>.js`): GitHub Pages sets its own cache headers, so a changed file gets a new name and a cached one is never stale. The generator rewrites the references in pages and between modules, and `check-site.py` fails a page that loads an unhashed asset. Until a module is ready the page says so and its controls stay disabled. The release build fails when any module is over its budget (the engine's is 1.5 MiB) and prints each module's size and headroom.

## Accessibility

Every page has a banner, navigation, main and footer landmark, one `h1` and headings in order, a skip link and a visible focus ring. Charts are labelled groups with a table view. Status and tier colours reach 4.5:1 against every surface in both themes, and motion stops under `prefers-reduced-motion`.

## Safety

Records, notices, claims and edited rules can carry attack payloads, so the site treats them as inert text.

- Every page carries a strict Content-Security-Policy: only the site's own scripts, styles and WASM modules, no inline script or style, no requests elsewhere.
- Generated pages escape every value; page scripts insert text, never HTML. URLs from records are shown defanged and never as links.

[`check-site.py`](../../scripts/ci/check-site.py) checks the sources in CI and the pre-commit hook, and every generated page and the build's inputs after a build. [`site-xss-check.mjs`](../../scripts/site-xss-check.mjs) builds the site with a hostile notice, loads every page in headless Chrome, drives the workbench with XSS probes, hostile claims and hostile edited rules, picks a hostile evidence bundle in the bundle viewer, checks the notice filters on synthetic notices (`crates/sc-publish/tests/fixtures/notices/`, never published), and fails if any of them runs; CI runs it at deploy.
